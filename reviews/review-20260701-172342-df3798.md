## Findings

### High - Local GPU generation serialization has a race

**Files:** `src/localgen.ts:33-38`, `src/dashboard.ts:2247-2263`, `src/dashboard.ts:2677-2706`, `src/dashboard.ts:2814-2855`

`run()` checks `_busy` before `await preflightGate()`, but only sets `_busy = true` after the await. Two concurrent requests can both observe `_busy === false`, both await the safety gate, then both set `_busy` and spawn local generation. This breaks the stated single-GPU serialization guarantee and can run two LTX/diffusers jobs at once, which is exactly the box-freeze scenario these guards are intended to prevent.

**Recommendation:** acquire the in-process busy lock before any await, release it immediately if preflight fails, and release it exactly once when the child callback completes. Keep the external heavy-job lock as a second layer, not the only serialization.

### High - SQL moderation exposes whole writable databases, including the app DB

**File:** `src/sqlmonitor.ts:45-68`, `src/sqlmonitor.ts:443-451`, `src/dashboard.ts:2485-2508`

The moderation API treats `writable: true` as permission to update/delete/insert any non-`sqlite_%` table in that DB. The registry marks both `massage` and `claudeclaw` as writable, so an authenticated browser or script can mutate arbitrary tables in the core ClaudeClaw store, not just narrowly intended moderation rows. The UI confirm is client-side only and is bypassed by direct API calls.

This is a design flaw rather than a style issue: a compromised master session, accidental browser automation, or a future UI bug can delete sessions, tasks, token usage, agent file history, dashboard settings, etc. The comment says "curated allowlist", but the enforcement is DB-level, not table/column/action-level.

**Recommendation:** replace the boolean with a server-side moderation policy per table: allowed columns and allowed actions. Remove `writable: true` from `claudeclaw` until specific tables are intentionally exposed.

### High - SQL row edits and undo can clobber concurrent changes and primary keys

**File:** `src/sqlmonitor.ts:540-568`, `src/sqlmonitor.ts:577-597`, `src/sqlmonitor.ts:654-695`

`updateRow()` fetches a before-image, then updates by rowid/PK only. It does not verify that the row still matches what the operator reviewed, and it allows changes to primary-key columns. `undoMutation()` similarly restores the old image without checking that the current row still matches the mutation's recorded `after_json`.

Failure modes:

- Operator A loads a row, app/user changes it, Operator A saves stale data and silently overwrites the newer app/user change.
- A primary-key update succeeds, then `fetchRow()` with the old key returns null and the audit entry has an unusable after-image.
- Undo of an older mutation rolls back fields that were legitimately edited later.

**Recommendation:** add optimistic concurrency. The client should send the reviewed before-image or a stable hash; the server should reject if the current row differs. Disallow updates to key columns by default. Undo should only proceed if current row equals the stored `after_json`, otherwise require manual conflict resolution.

### Medium - "Before write" backups are throttled and can silently lie

**File:** `src/sqlmonitor.ts:418-434`; related: `src/massage-admin.ts:208-218`

`backupBeforeWrite()` reuses a DB snapshot for up to 60 seconds. That means the second and later writes in the window are not backed up "before the write" despite the audit row saying they are. Worse, if both `src.backup(dest)` and `copyFileSync()` fail, the function still returns `dest`, so audit entries can reference a backup path that does not exist.

`massage-admin` separately prefers raw file copy of the main DB and WAL (`copyFileSync`) over SQLite's online backup API. Copying main/WAL while another process writes is not a consistent snapshot, and the fallback `db.backup(dest)` is fire-and-forget, so it can still be incomplete after the update returns.

**Recommendation:** make backup success explicit. Either snapshot every write or call the field `lastSnapshotPath` and rely on before-image for row undo. For SQLite backups, prefer `await db.backup(dest)` and fail the mutation if a promised backup cannot be created.

### Medium - SELECT-only SQL can still block the Node event loop

**File:** `src/sqlmonitor.ts:341-361`

The SELECT guard blocks write keywords and caps returned rows at 500, but the query executes synchronously in the dashboard process via `better-sqlite3`. A heavy read such as a large cross join, unindexed predicate, recursive CTE, or aggregate can run for seconds/minutes before yielding any rows. While it runs, the Node event loop is blocked: auth, chat, controls, and health endpoints stall.

The row cap does not bound execution cost; it only bounds response size after SQLite has found rows.

**Recommendation:** execute ad hoc SQL in a worker/subprocess with a hard timeout and interruption, or enforce a stricter query profile for the dashboard (required `LIMIT`, SQL length cap, no recursive CTEs, no cross joins, and a low statement timeout).

### Medium - RapidAPI proxy has unbounded cache/quota burn surface

**File:** `src/rapidapi.ts:284-303`, `src/dashboard.ts:2899-2907`

`CACHE` is a process-global `Map` with no maximum size and expired entries are never swept unless hit again. Each unique query can store up to dozens of upstream results for 10 minutes. A single authenticated page, script, or accidental polling loop can issue many unique queries, burn RapidAPI quota, and grow memory without bound.

There is also no query length cap or in-flight coalescing, so repeated simultaneous searches for the same cold key fan out to upstream.

**Recommendation:** cap query length, cap cache entries with LRU eviction, coalesce in-flight requests per cache key, and consider a per-session/IP rate limit for `/api/rapidapi/search`.

### Low - External video embeds are unsandboxed

**File:** `web/src/pages/RapidApi.tsx:91-99`

RapidAPI results render third-party adult-site embeds in unrestricted iframes. Cross-origin isolation protects the parent DOM, but an unsandboxed iframe still gets its full provider script environment, can attempt top navigation with user activation, open popups, and generally runs with more capability than the dashboard needs.

**Recommendation:** add an iframe `sandbox` policy and narrow `allow` to the capabilities actually required for playback.
