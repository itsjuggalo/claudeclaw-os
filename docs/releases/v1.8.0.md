# v1.8.0: Claude and Codex, one fleet

**Theme:** Run any agent on OpenAI (Codex) instead of Claude, or mix both in one fleet, with live streaming on by default.

**Bundles:** #174.

---

> ## 🚨 v0 release of Codex support
> Native OpenAI (Codex) ships as a **v0**. It is ready for early use, but it is new and environment-sensitive. Follow the setup steps closely, and if you run several agents, move **one** agent to Codex first and exercise it before switching the rest.

## Highlights

**🤖 ClaudeClaw runs on OpenAI now, not just Claude.**
Any agent can run on a GPT model through Codex instead of Claude. Keep some agents on Claude, put others on Codex, or mix both in the same fleet, and they still share the same Telegram, dashboard, missions, scheduling, memory, and coordination. Codex runs through one of two transports set in your `.env`: try **App Server** for real token-level streaming, with **SDK** as a proven fallback.

**🎚 Switch agents one at a time.**
Provider and model are set per agent in `/dashboard`, under Agents (for each sub-agent) or Settings (which controls your **primary agent only**). There is no fleet-wide switch on purpose. Move one agent to Codex, test its conversations, tools, permissions, and scheduled work, then roll out to the rest.

**⚡ Live responses are on by default.**
You see the answer as it is written, with a live progress line and an elapsed clock, instead of waiting on a blank screen. Activity and tool calling are now inlined with the message turn, no more notification blasts. App Server gives true token-level streaming; the SDK transport still works but may deliver the whole reply at once. Set `STREAM_STRATEGY=off` to go back to the old batched view (Telegram sends text only when the turn completes).

**🎛 Refreshed model catalog and per-agent controls.**
The selectable model list and runtime controls are refreshed across Telegram and the dashboard, so picking the right model per role is simpler. Same-provider model changes apply next turn; provider or reasoning changes take a `/newchat`. In Telegram and Signal, `/model` switches the model and resets it back to the default; `/provider` is display-only for now.

**🔒 Provider-aware permissions.**
Tool permissions are enforced per provider with a shared policy, so a Codex agent and a Claude agent follow the same rules. Dispatch is authorized before work reaches the model, and the App Server sandbox is verified before every turn (it fails closed in both directions).

---

## 🛠 Upgrading? Two required steps

1. **Run `npm install` and `npm run migrate` before restarting.** ClaudeClaw refuses to start while a migration is pending, and under a process manager like PM2 that means a restart loop until you migrate. Migrate first, then restart.
2. **Streaming turns on automatically** for every install on upgrade, including Claude-only ones. Set `STREAM_STRATEGY=off` to keep the old batched view.

The v1.8.0 migration only quotes legacy unquoted Windows `CLAUDECLAW_CONFIG` paths, leaves quoted / macOS / Linux values alone, and writes `.env.pre-v1.8.0.bak` first.

# Details

## Native OpenAI support

OpenAI is now a first-class ClaudeClaw provider. Agents authenticate using either an existing `codex login` or `OPENAI_API_KEY`.

Codex is supported through **two transports**, selected with `CODEX_TRANSPORT` in your `.env`. They deliver the same auth, the same per-agent config, and the same tools and permissions, only the delivery mechanism differs. Start with App Server; if your environment gives you trouble, fall back to SDK.

**App Server (try this first):**

```dotenv
CODEX_TRANSPORT=app-server
```

A persistent `codex app-server` process that stays warm across turns. It provides real incremental (token-level) text streaming, live tool progress, turn cancellation, compaction telemetry, and effective-policy verification before each turn. This is the richer, more responsive experience.

**SDK (fallback):**

```dotenv
CODEX_TRANSPORT=sdk
```

Spawns a fresh `codex exec` once per turn. Simpler and battle-tested, but it delivers the reply as a single block rather than streaming token by token. It is the proven rollback path, and the default if `CODEX_TRANSPORT` is unset. Switch to it if App Server misbehaves in your environment.

**Why two:** App Server is a live connection to a running Codex process, which is what makes real-time streaming, progress, and per-turn policy checks possible. SDK is the simpler per-turn spawn with no long-lived process to manage. Keeping both means you get the richer experience where it works and a dependable fallback where it does not.

**Its own sandbox:** either transport runs Codex inside Codex's own harness sandbox, an isolated `CODEX_HOME` with OS-level containment (read-only / workspace-write / danger-full-access), separate from the Claude path. What an agent is allowed to write depends on your platform and the `CODEX_DANGER_WRITE` setting, see **[Write access by platform](#write-access-by-platform)** below.

The experimental `acp-codex` provider is separate from this native OpenAI integration and is not required.

## Mixed-provider agent fleets

Each agent can independently run on Claude or OpenAI. Use Claude for some roles and OpenAI for others while keeping the same Telegram, Dashboard, mission, scheduling, memory, and coordination surfaces. Provider and model identity are resolved per turn, so agents do not rely on stale conversational memory to identify themselves.

## Live response streaming

Streaming is now enabled by default. ClaudeClaw displays assistant text as it arrives, the current tool or work activity, an elapsed-time indicator during longer turns, and completed activity in a compact turn ledger.

OpenAI App Server provides real incremental assistant-text streaming. The SDK transport remains supported but may deliver completed assistant messages rather than token-level updates. Disable the streaming interface with `STREAM_STRATEGY=off`.

## Improved model and runtime controls

The model catalog and runtime controls have been refreshed across Telegram and the Dashboard, with consistent behavior:

- Same-provider model changes apply to the next turn.
- Provider changes require `/newchat`.
- Reasoning-effort or thinking changes require `/newchat`.
- `/model reset` restores the provider default.
- Agent cards show the selected model and only the controls that model supports.
- Unsupported controls are omitted instead of displaying invalid state.

## Cross-provider missions and scheduling

Claude and OpenAI agents coordinate through the same orchestration layer, missions, schedules, and the shared Hive Mind.

**Codex agents already participate fully, with nothing to configure.** They write their own Hive Mind entries, and they create, receive, and schedule missions, out of the box. `DISPATCH_ALLOW_HIVE_READ` does **not** affect any of that.

What the flag controls is one specific action: a Codex agent **pulling the shared Hive Mind back into its turn** (reading everything the whole fleet has logged). That is different from writing, because to *read* the shared pool, its contents have to be handed to the model, which on a Codex agent means sent to the provider (OpenAI). Writing an entry leaks nothing; reading the shared pool would expose your fleet's collective memory to a third party. So that one read is off by default:

```dotenv
DISPATCH_ALLOW_HIVE_READ=true
```

In short: **off** = Codex agents write to and act on the hive, but cannot read the shared history back into the model (the safe default, no action needed). **On** = Codex agents can also read the shared hive, accepting that its contents leave your machine. Claude agents read and write the Hive Mind normally either way; this only concerns non-Claude providers.

**Why only non-Claude providers, and will this change?** ClaudeClaw runs on Anthropic, so a Claude agent reading the hive keeps that data with the provider you already run on. A Codex agent adds a second provider (OpenAI), so reading the shared hive would route your fleet's memory somewhere new, that is the line this flag draws, not that Claude is inherently safer. Native Codex is a v0; as it matures toward parity with the Claude path, these controls may change in future releases.

Dispatch authorization is enforced before work reaches the provider. Restricted callers cannot gain additional authority through the model runtime.

## Security and permissions

The native OpenAI provider uses shared ClaudeClaw capability profiles with provider-specific enforcement. The runtime now:

- verifies the effective App Server sandbox before each turn
- rejects both permission escalation and silent permission reduction
- keeps tool-less and read-only callers isolated
- disables host applications and account enumeration for restricted callers
- disables shell execution when the caller does not permit it
- keeps web search disabled unless explicitly authorized
- exposes only approved MCP servers
- authorizes dispatch before provider execution
- interrupts only the intended App Server turn during cancellation

### Write access by platform

The shipped default is `CODEX_DANGER_WRITE=false`. On macOS, Linux, and WSL2 that is all you need, Codex runs in its contained `workspace-write` sandbox and eligible agents can write within the workspace.

**Native Windows (PowerShell) currently needs a different setting to reach parity with the Claude path.** Codex's contained `workspace-write` sandbox is not yet available on native Windows (an upstream Codex limitation being worked on). Until it lands, a native-Windows Codex agent resolves to **read-only** unless you opt in, meaning it can read and converse but cannot write files, run commands, or carry out the write-backed actions the fleet depends on, mission tasks and scheduled jobs among them. To give a trusted native-Windows agent the same working capability as a Claude agent, set:

```dotenv
CODEX_DANGER_WRITE=true
```

This drops the OS sandbox and grants full machine access, so use it only for agents you trust. It is the same posture the Claude path already runs under (Claude executes without an OS sandbox), so it is parity, not a step down. If you would rather keep a contained sandbox on Windows, run the agent under WSL2 instead. As native-Windows sandboxing matures upstream, this requirement is expected to relax in a future release.

## Owner identity

Fresh setup now stores the owner name collected by the setup wizard, providing a deterministic owner label in shared surfaces such as text War Room conversations. Existing installations can set it manually:

```dotenv
CLAUDECLAW_OWNER_NAME=<USER-NAME>
```

## Known limitations

- **Codex is v0** and environment-sensitive; follow the setup steps and pilot one agent before rolling out across a fleet.
- Native Windows cannot currently provide contained Codex writes. Use trusted `CODEX_DANGER_WRITE=true` access or run under WSL2.
- Voice / War Room voice mode remains experimental; its current Python runtime/environment work is deferred to a follow-up. Text interaction is unaffected.
- Dependency security findings are tracked for a focused patch release rather than forcing breaking dependency upgrades into this validated release.
- App Server remains opt-in while the SDK stays the default and rollback path.
